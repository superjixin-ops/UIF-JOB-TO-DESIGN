# 设计哲学：为什么这么做，遵从什么，怎么解决

> 这份文档不是功能清单，是**决策依据**。
> 面试官问"为什么"的时候，答案在这里；代码注释也按同一套结构写。

---

## 0. 一条主线

这个项目里几乎每个决定，都可以归到同一个问题：

> **这件事，出问题时有人能回答吗？**

- 文档错一列 → 能不能追溯到哪一行？
- 模型说完成了 → 谁来判断真的完成了？
- 服务变慢了 → 能不能说出多慢、从什么时候开始？
- 数据丢了 → 能不能恢复，恢复过吗？
- 这个改动有用吗 → 有没有对照实验？

答不上来的，就是没做完。

---

## 1. 确定性优先

### 问题

第一版让模型读 YAML 直接写文档。它数 30 列能对，数 100 列必错；
同一份输入跑两次，列数可能不一样。

### 原则

> **能用代码算的，绝不交给模型。**

模型的职责收缩到两件真正需要判断的事：

1. 先查什么（决定路径）
2. 怎么把结论说成人话（叙述）

### 怎么落地

| 层 | 谁做 | 为什么 |
|---|---|---|
| 解析 YAML | `parser.py` | 事实必须可复现 |
| 数列 / 比差异 | `checks.py` | 精确计算不能靠概率 |
| 渲染 xlsx | `render.py` | 文件格式不需要判断 |
| 决定顺序 / 措辞 | 模型 | 这两件写不出规则 |

### 代价

- 代码量变大（解析器 + 校验器 + IR 比"一个 prompt"多十倍）
- 灵活性下降：新格式要改代码，不是改 prompt

### 什么时候不该这样

任务本身是开放式的（"从一堆日志里找异常"），没有确定的中间表示——
这时强行代码化会把系统做死。**先问：这件事有确定的中间结果吗？**

---

## 2. 裁判先行

### 问题

让模型"自己检查自己"，它会说"我检查过了，没问题"。
这不是校验，是自我评价。

### 原则

> **先写裁判，再写生成。裁判必须是模型说服不了的代码。**

### 怎么落地

```
生成 → 校验（代码） → 不通过 → 把错误清单退回 → 再生成
                  → 通过 → finish 才被接受
```

三个细节：

1. `finish` 会**重新跑一次**校验，不相信上一次的结果
2. 循环的退出条件是"校验通过"，不是"模型不调工具了"
3. 同一组错误连续 3 轮 → 强制整篇重写（局部修补已证明无效）

### 代价

- 裁判本身可能错（我们踩过：规则来自三个样例的归纳，真实语料 14% 不满足）
- 裁判太严会逼模型编造（"比输入更正确"）

### 对应的教训

**校验器只能校验你真正要求的东西。**
要求"忠实实现"，就不能同时要求"比输入更正确"。

## 3. 证据优先

### 问题

模型写"这里少了 8 列"。哪 8 列？哪一行？它答不出来。
不可追溯的结论，等于不可信。

### 原则

> **每一条结论，都要能指回一个可验证的来源。**

### 怎么落地

| 结论类型 | 证据 |
|---|---|
| 列差异 | `checks.schema_diff` 的计算结果 |
| 规则引用 | 检索到的 chunk id |
| 生成的 YAML | 设计文档的哪一行 |
| 自由文本 | 实体必须在原文里字面出现 |

四类检查：规则存在性、列名对齐、数字复算、证据路径。
全部是代码，没有一条让模型参与判分。

### 代价

- 需要设计 IR（中间表示），不能直接拼字符串
- 有些"感觉对"的结论会因为找不到证据而被丢弃——这是故意的

---

## 4. 负结果优先

### 问题

"我提升了 40%"是最容易说的，也是最容易假的。
检索指标提升 40%，端到端可能一点变化都没有。

### 原则

> **没有对照实验的优化，不上线。**

### 怎么落地

| 改动 | 指标变化 | 端到端 | 结论 |
|---|---|---|---|
| 混合检索 α=0.1 | R@5 0.667 → 0.933 | t=0.63 不显著 | **不上线** |
| few-shot 结构近邻 | top-3 更相似 | 91% vs 91% | **不为它上向量库** |
| 增量索引 | 5 分钟 → 2 秒 | 直接可测 | 上线 |

### 代价

- 每个改动都要写评测，时间成本高
- 有些结论是"不知道"，不能写成"有效"

### 为什么这反而加分

面试官见多了"我用了 X，效果提升 Y%"。
能说"我试了，没用，所以没上"的人，通常真的做过。

## 5. 可回答优先（企业级）

### 问题

"企业级"经常被理解成"功能多"：多租户、K8s、微服务。
但出问题时，这些一个都回答不了"是谁、什么时候、做了什么"。

### 原则

> **企业级 = 每个能力都能回答：为什么需要、怎么验证。**

### 怎么落地

| 问题 | 能力 | 验证方式 |
|---|---|---|
| 这是谁操作的 | RBAC + 审计哈希链 | 改一条审计，验证链断裂 |
| 服务怎么样 | 指标 + 告警 | `check_alerts` 退出码 |
| 数据丢了 | 备份 + 恢复 | CI 里真的恢复一次 |
| 配置错了 | 启动校验 | `pdc doctor` 一次报全部 |

### 刻意不做

多租户、水平扩展、K8s：没有第二个用户、没有负载。
做了也无法验证隔离和扩展是否有效——**那是企业级表演**。

## 6. 这套哲学怎么体现在文档里

你看到的每份文档都是同一个结构：

```
事故场景（为什么需要）
  -> 方案对比（有哪些选项）
  -> 实现（怎么做的）
  -> 验证（怎么证明）
  -> 代价与局限（诚实）
  -> 面试话术（怎么讲）
```

不是"功能说明书"，是**决策记录**。

对应文件：

| 文档 | 回答什么 |

| `docs/hallucination-and-testing.md` | 幻觉怎么治理、测试怎么防自欺 |

| `docs/learning-path.md` | 从零到面试的学习顺序 |

---

## 7. 一句话总结

> **确定性优先**让结果可复现；
> **裁判先行**让完成可判定；
> **证据优先**让结论可追溯；
> **负结果优先**让优化可信；
> **可回答优先**让系统可运维。

五条合起来，就是"这个项目为什么值得信"。
