# 记忆检索：从"全量注入"到"按相关性召回"

> 对应面试模块 5（记忆系统）。这份文档回答：为什么要检索、四路信号怎么定权、什么时候不该上向量。

---

## 1. 事故场景

### 场景 A：多轮任务反复交代背景

```
第 1 轮：把这个 pipeline 的 schema 漂移修一下
第 2 轮：刚才那个漂移，下游影响哪些表？
```

没有记忆，第 2 轮的"刚才那个"没有任何指代。

### 场景 B：相似任务的历史结论找不到

```
上周做过 inventory snapshot，结论是"仓库维度要按 SKU 对齐"
今天做类似的任务，模型从零开始，又踩了一遍
```

有 JSONL 落盘，但没有检索——**存了等于没存**。

### 场景 C：全量注入把 token 吃光

会话一长，把所有历史都拼进 prompt：

- 5000 token 的历史里，只有 200 token 相关
- 剩下的既是成本，也是噪音，还会稀释指令

**结论：记忆必须有"取哪一段"的策略，而不是"全放进去"。**

---

## 2. 四层记忆，分别解决什么

| 层 | 实现 | 解决 | 生命周期 |
|---|---|---|---|
| 工作记忆 | 当前 prompt | 这一轮要用的上下文 | 请求级 |
| 短期记忆 | 滑窗（`keep_turns`） | 最近几轮指代 | 会话内 |
| 摘要记忆 | 溢出时压缩 | 长会话不爆 token | 会话内 |
| **长期记忆** | JSONL + **检索** | 跨会话复用 | 永久 |

前面三层在 `pdc/memory.py` 的 `Memory` 里，本文讲第四层。

## 3. 为什么是四路信号

```python
score = 0.45 * 词面 + 0.35 * 向量 + 0.15 * 时间衰减 + 0.05 * 同会话加成
```

### 词面（0.45）

技术讨论里最关键的词往往是**专有名词**：

```
SK_ORDER_DATE、fact-order-fulfillment、diff_schema
```

这些词在 embedding 模型里很弱（低频 token、分词后会碎），但词面匹配一抓一个准。

### 向量（0.35）

同一个结论会换说法：

```
"schema 漂移" / "列对不上" / "声明的列和实际不一致"
```

词面匹配漏掉的，向量补。

**两路是互补的，不是二选一。** 只用向量，专有名词会漏；只用词面，同义表达会漏。

### 时间衰减（0.15）

```
recency = 0.5 ** (age_days / 7)
```

一周前权重 0.5，两周前 0.25，一个月前 0.06。

**为什么需要**：三个月前的结论可能已经过期（表结构改了、口径变了）。
不衰减的话，旧结论会和新结论同分，排序变成随机的。

### 同会话加成（0.05）

同一个会话里的记忆通常更相关（同一个任务线）。
权重很小，只做 tie-breaker。

### 为什么没有"重要性"

生成式 Agent 的经典公式是 `recency + importance + relevance`。
但 importance 需要额外信号：

| 方案 | 问题 |
|---|---|
| 让模型打分 | 每条记忆一次调用，成本和延迟都高 |
| 按长度/数字启发式 | 和"重要性"相关性很弱，是噪音 |
| 人工标注 | 不现实 |

**没有可信信号时不编一个。** 少一路信号，比加一路噪音好。

## 4. 三个工程细节

### 4.1 降级不能阻断

```python
try:
    vec = embedder.encode(...)
except Exception:
    vec = None      # 整路降级，不是整个检索失败
```

embedder 不可用时（模型没下载、内网不通），权重按比例分给其余三路，
分数尺度不变，排序仍然可用。

### 4.2 去重

同一个结论会被写进多个会话（"这个 pipeline 又要改一次"）。
不去重的话，top-3 可能是同一句话的三份拷贝。

做法：内容归一化（小写 + 只留字母数字）取前 120 字符做 key，保留分最高的一条。

### 4.3 记忆是数据，不是指令

召回的内容会拼进 prompt。它来自历史用户输入，**可能是注入源**。

```python
wrap_untrusted(body, label="memory")
```

和工具返回值一样处理：明确告诉模型"这是资料，不是命令"。

## 5. 为什么 API 只用词面，CLI 用向量

| 环境 | 用什么 | 原因 |
|---|---|---|
| CLI（单线程） | 词面 + 向量 + 衰减 | 只加载一次模型，值得 |
| API（多 worker） | 词面 + 衰减 | 每个 worker 各加载 100MB 模型不划算 |

这是一个**有意识的取舍**，不是漏做。

如果以后 API 也要向量：

1. 把 embedding 做成独立服务（一个进程加载模型，HTTP 调用）；
2. 或者把记忆向量预先算好存起来，查询时只做点积。

第 2 种更简单：写入记忆时算一次，存进 JSONL；查询时只 embed query。

```bash
# 1. 造两条会话
uv run python -c "
from pdc.memory import SessionStore, Memory
s = SessionStore('out/memory')
```

## 7. 代价与局限

| 局限 | 说明 |
|---|---|
| 没有遗忘 | 错误结论会一直留着，只能靠时间衰减压低 |
| 没有冲突消解 | "A 说 7 列，B 说 8 列"两条都会召回，模型自己判断 |
| 没有反馈 | 用户说"这条没用"不会降低它的权重 |
| O(n) 扫描 | 每次检索读所有会话；几万条以后要上索引 |
| 没有分用户隔离 | 目前是所有会话一个池子；多用户要加租户过滤 |

这些不是"没想到"，是"现在没有信号/规模去做"。
写出来比假装没有好。

---

## 8. 面试话术

> "长期记忆不能全量注入——5000 token 里可能只有 200 相关。
> 我用四路信号做召回：词面、向量、时间衰减、同会话加成。
>
> 词面和向量是互补的：专有名词靠词面，同义表达靠向量。
> 没有加 importance，因为拿不到可信信号，加一路噪音不如不加。
>
> API 和 CLI 策略不同：CLI 单线程可以加载向量模型，API 多 worker
> 各加载一份不划算，所以 API 只用词面 + 衰减。这是取舍，不是漏做。"
