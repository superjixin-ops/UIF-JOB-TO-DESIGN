## 0. 一句话

> 让模型写 YAML，让代码判对错。
> **模型的每一次"我觉得可以了"，都必须先过一遍它无法说服的裁判。**

---

## 1. 为什么加这个方向

原来那个项目（YAML → 设计文档）有一个说不清的地方：**最终产物是代码算的**。
模型只负责决定先查什么、怎么叙述。这在工程上是对的，但拿去面试会被一句话问穿：

> "所以你的 Agent 到底产出了什么？"

新方向把这个关系翻过来：

| 判定项 | design 方向 | **build 方向** |
|---|---|---|
| 最终产物谁写的 | 代码 | **模型** |
| 路径谁决定 | 固定 SOP | 模型自己选示例、自己决定改哪 |
| 什么时候算完 | 步数用完 | **校验器通过**（断言） |
| 能不能装 | 能 | **不能**：YAML 解析不了就是解析不了 |

这不是"再加一个功能"，是补上项目里唯一缺失的东西：**一个产物由模型生成、
失败无法伪装的闭环**。

---

## 2. 三个角色

```
        设计文档 (xlsx / md)
                │
                ▼
    ┌───────────────────────┐
    │  Requirement           │  把文档读成结构化需求
    │  design_reader.py      │  读不出来就报错，绝不猜
    └───────────┬───────────┘
                ▼
    ┌───────────────────────┐
    │  Generator (模型)      │  write_yaml / read_example / ...
    │  yamlgen.run_build     │
    └───────────┬───────────┘
                │ 候选 YAML
                ▼
    ┌───────────────────────┐
    │  Judge (确定性代码)     │  spec_validator  结构 / 命名 / 安全
    │  两个文件，零模型       │  spec_grounding  事实对齐 / 语义完整
    └───────────┬───────────┘
                │ 通过 / 错误清单（带 code + fix）
                ▼
          finish 门禁
```

三个角色必须分开写。**一旦让模型参与判分，治理就结束了。**

## 3. 全过程：从零到 143 个键值零差异

这一节按时间顺序记录整个治理过程，**包括走错的弯路**。

看的时候请留意一条贯穿全程的规律：

> 几乎每一个"模型的问题"，最后查下去都不是模型的问题。
> 是文档缺字段、是校验器太严、是错误信息写错、是 prompt 的形状不对。

这也是为什么我把过程写得这么细——**结论只能告诉你做什么，过程才能告诉你下一次怎么查。**

---

### 3.1 阶段 0：先写裁判，再写生成

**目标**：在写任何一句 prompt 之前，先让"对错"可判定。

**动作**（顺序不能反）：

1. `design_reader.py` —— 把设计文档读成结构化需求。
   原则是**宽松读、严格报**：表头多空格、大小写不一致都能容忍；
   但必需列缺失时直接抛 `SpecReadError`，绝不猜。
2. `spec_validator.py` —— 结构 / 契约 / 命名 / 安全四类检查。
   每条返回 `code + message + fix + severity`。
3. `spec_grounding.py` —— 拿文档逐项核对生成的 YAML。
   把错误分成"漏"和"编"，因为它们的危险度不同。

**立刻做了一次自检**（这一步很多人会跳过）：

```
YAML → xlsx → 读回 spec → 拿 spec 核对原始 YAML → 应该 0 违规
```

4 条样例全部 0 违规。

**为什么这一步关键**：如果读文档就丢了列，模型再强也生成不对，
而失败会被误记成"模型能力不行"。**先证明输入没丢，再谈生成。**

**留下的规则**：

> 裁判先行。没有裁判的生成循环，只是一次性的 demo。

---

### 3.2 阶段 1：第一次跑通，1 轮就过 —— 这不是好消息

**动作**：`pdc build out/roundtrip/dim-product-family.xlsx`

**结果**：

```
status=passed  rounds=1  steps=5  tokens=13,180  latency=8.5s
```

**第一反应**：成了。

**第二反应**（也是这次最重要的一次怀疑）：太快了，而且这条样例只有 5 列。

**动作**：`diff` 产物和源文件。

```
74 行  samples/pipelines/dim-product-family.yaml
74 行  out/dim-product-family.yaml
（逐字节相同）
```

**判断**：这不是生成，是抄。参考示例目录 `samples/pipelines/` 里就有这条样例的源文件，
模型 `list_examples` 看到了它，`read_example` 读回来，原样提交。

**这说明什么**：所有指标（通过率、grounding、轮数）全是满分，
但**指标本身没有能力发现"答案是抄的"**。必须有一个专门测这件事的指标。

**留下的规则**：

> 满分是最危险的信号。先怀疑测试，再庆祝。

---

### 3.3 阶段 2：注入审计 —— 先证明检测器会响

**目标**：在相信"通过"之前，先证明"不通过"是可能的。

**动作**：拿一份判通过的产物，手工注入四类错误：

| 注入 | 期望 | 实际 |
|---|---|---|
| 加一列 `MADE_UP_COLUMN` | 编造被抓 | `S_COL_EXTRA` ✅ |
| 删掉一列 `CHANNEL` | 遗漏被抓 | `S_COL_MISSING` ✅ |
| 删掉 `RenameColumns.mapColumns` | 语义丢失被抓 | 当时**没抓住** ❌ |
| `overwrite` 改成 `append` | 失真被抓 | `S_LOAD_MODE` ✅ |

第三行就是下一个阶段的入口。

**判断**：4 类里抓住 3 类。**"抓住 3/4"比"全过"有用得多**，
因为它精确指出了下一个要补的地方。

**留下的规则**：

> 检测器要先自证会响，再谈准确率。
> 一个从不报警的检测器，和一个没有检测器，看起来是一样的。

---

### 3.4 阶段 3：留一法 —— 把"抄答案"这条路堵死

**动作**：改评测。生成 A 时，示例目录里只放 B/C/D。

**新增指标**：`exact_match_rate` —— 与源文件逐字节相同的比例，**必须为 0**。

**结果**（第一次真正跑）：

```
[PASS] dim-customer-segment   rounds=1  tokens=41,669  exact=False
[PASS] dim-product-family     rounds=4  tokens=92,628  exact=False
（第 3 条时 DeepSeek 返回 402 Insufficient Balance，中断）
```

**判断**：`exact=False` 说明不再抄了。但 `dim-product-family` 从 1 轮变成 4 轮，
说明之前的 1 轮是抄出来的假象。

**留下的规则**：

> 评测集必须和参考示例隔离。
> 隔离不了，就加一个"是否逐字节相同"的指标——它比任何准确率都先发现问题。

---

### 3.5 阶段 4：第一次真实失败 —— 8 轮、51 万 token、一条改不对的规则

**动作**：用留一法跑 `fact-order-fulfillment`（3 个 job、30 列、11 步变换）。

这一条是整个项目里最长的一次调试，前后四轮，每次只前进一步。

**(a) 第一次：11 轮、90 万 token，卡在一条"其实不该管"的规则**

```
status=failed  rounds=11  tokens=902,618
issues: W_SCHEMA  eid: 1 列在 schema 里但数据帧没有: ['SK_ORDER_FULFILLMENT']
```

**查**：这条流水线的源文件里本来就有这个缺陷（样例故意保留的真实缺陷），
设计文档甚至专门有一张 `Schema Diff` 表记录它。

**判断**：**校验器在要求模型"比输入更正确"。**
模型只有两条路：永远失败，或者偷偷加/删一列——后者是编造。

**修正**：`schema_diff` 从"生成门禁"移回"设计评审"。
生成方向只回答一个问题：**你有没有忠实实现这份文档。**

**(b) 第二次：还是失败，这次卡在 `schema_mismatch`**

7 列漂移。同一个病，换了个 code。

**修正**：`schema_mismatch` 也不再是生成门禁。理由同上。

**(c) 第三次：只剩一条**

```
status=failed  rounds=8  tokens=514,858
violations: S_PARTITION_BY  datamart-parquet: partition_by 应为 [...]，实际 []
```

**查产物**：模型确实没写 `partitionBy`。文档里有，所以这次真的是模型的锅。

**但为什么 8 轮改不对？** 去看错误信息：

```
partition_by 应为 [('SK_ORDER_DATE',)]，实际 []
```

`partition_by` 是 Python 属性名。YAML 里的键叫 `partitionBy`，
而且必须写在 `load.connections[0]` 下面。**模型知道少了分区，但不知道往哪儿放。**

**留下的规则**：

> 校验器只能校验你真正要求的东西。
> 要求"忠实实现"，就不能同时要求"比输入更正确"。

---

### 3.6 阶段 5：改一句话，8 轮变 2 轮

**动作**：把错误信息改成可直接照做的写法。

```
datamart-parquet: 在 load.connections[0] 下写 partitionBy: ['SK_ORDER_DATE']，当前是缺失
```

**结果**：

| 版本 | 轮数 | token | 结果 |
|---|---|---|---|
| `partition_by 应为 [...]` | 8（上限） | 514,858 | 失败 |
| `在 load.connections[0] 下写 partitionBy: [...]` | 2 | 76,809 | 通过 |

**同一个模型、同一个输入、同一份文档。**

**判断**：Agent 的效果有一半取决于工具反馈的质量。
这不是"模型不行"，是"反馈没设计好"。

**留下的规则**：

> 错误信息三件套：**YAML 里的键名 + 它所在的位置 + 期望值**。
> 缺任何一个，模型都要靠猜。

---

### 3.7 阶段 6：参数级比对 —— "能解析"不等于"能跑"

**动作**：把阶段 2 没抓住的那一类补上：删掉 `mapColumns` 会怎样。

**观察**：产物完全合法，四层检查全过。

**但**：`mapColumns` 是 `ORDER_LINE_ID → ORDER_LINE_NUMBER` 的唯一来源。
映射没了，schema 里引用的新列名在数据帧里根本不存在。

**为什么校验器没报**：它只检查"列名集合对不对"，
不检查"变换有没有把列造出来"。`transformType` 还在，所以连 `TRANSFORM_MISSING` 都不触发。

**修正**：加参数级比对。

```python
for t in spec.transforms:
    cands = [x for x in j.transforms if x.transform_type == t.transform_type]
    if any(_params_match(t.params, x.detail) for x in cands):
        continue
    → S_TRANSFORM_PARAMS
```

**验证方式（关键）**：拿**之前被判通过的那份 YAML** 重跑新校验器。

```
新增 21 条违规，其中 9 条是漏列
```

**留下的规则**：

> 改完裁判，一定要用**旧产物**回测。
> 否则你不知道标准是变严了，还是变松了。

---

### 3.8 阶段 7：文档补 Params —— 裁判逼着文档变完整

**动作**：给 `spec.transforms` 加参数。结果发现 `params` 是空的。

**查**：`build_transform_chain` 里写着

```python
detail = ", ".join(f"{k}={v}" for k, v in t.detail.items() if not isinstance(v, (dict, list)))
```

为了人类可读，**所有 dict / list 参数被丢掉了**。
而 `columns`、`mapColumns`、`columnsToSelect` 恰恰全是 list/dict。

**判断**：**设计文档本身是有损的。**
正向（YAML→文档）一年都发现不了，因为人看不出来少了个映射；
反向（文档→YAML）一跑就暴露。

**修正**：`Transform Chain` 增加 `Params` 列存完整 JSON，`Detail` 保留人类可读版本。

> 一列给人，一列给机器。

**留下的规则**：

> 单向的测试只能证明单向的正确。
> 只要有"生成"和"还原"两个方向，就必须做双向一致性测试。

### 3.9 阶段 8：上下文瘦身 —— 省下的 token 又还回去了

**现象**：一次失败运行烧掉 90 万输入 token。原因：模型每轮都整篇重写 YAML，
历史里堆着 8 个完整版本。

**修正**：`write_yaml` 的正文不进消息历史，只留字符数。

**踩的坑（这次是我自己的 bug）**：占位符写成

```python
return {"text": "<已提交 11955 字符...>"}
```

模型下一轮**把这个占位字符串当成自己的 YAML 又提交了一遍**，
校验器报"YAML 无法解析"，连续 8 轮卡死。

**根因**：模型会模仿它看到的**上一次工具调用参数**。
你把占位符放在 `text` 里，它就把占位符当 `text`。

**正确写法**：占位符不能放在原字段位置上。

```python
return {"__omitted__": 11955, "__note__": "上一轮正文已保存，不要复用这个参数对象"}
```

**第二个坑**：为了省 token，我一开始"只保留最新一次示例"，把旧的擦掉。
模型发现上一个示例消失了，就回头再读；读回来又把新的擦掉——**振荡**。
实测 34 步里 `read_example` 调了 36 次，`write_yaml` 0 次。

**修正**：保留最近两次示例；累计 4 次后把 `read_example` 从工具 schema 里**摘掉**。

**为什么是摘掉而不是报错**：实测"返回错误"没用——模型会把错误理解成"这次没读到，再试一次"，
又调了 10 次。**护栏要改变可选空间，不能只是拒绝。**

**留下的规则**：

> 压缩后的内容仍然是模型的模仿对象。
> 上下文管理不是删字，是改变它看到的世界。

### 3.10 阶段 9：完整评测 0.75 —— 第二次"把假设当规范"

**动作**：充值后完整跑 4 条留一法。

```
[PASS] dim-customer-segment
[PASS] dim-product-family
[FAIL] fact-inventory-snapshot   5 轮 / 339,990 token
[PASS] fact-order-fulfillment
pass_rate 0.75
```

**查失败原因**：

```
E_MAIN_DF  job eid 有 2 个 main_df: true
```

**查源文件**：这条流水线有**两个事实源**（库存快照 + 库存调整），
两个都标了 `main_df: true`，后面 join 在一起。

**查校验器**：写着"每个 job 有且只有一个主数据集"。

**这条规则哪来的**：我从另外三个样例里总结的。
写进裁判的那一刻，它就从"观察"变成了"硬约束"。

**判断**：这是阶段 4 的同一个病，**第二次发作**。
上次是 schema 规则，这次是 main_df 规则。

**修正**：只检查"至少有一个"，具体哪几个交给文档逐项比对。

| | 修之前 | 修之后 |
|---|---|---|
| pass_rate | 0.75 | 1.00 |
| 失败用例 | 5 轮 / 34 万 token | 1 轮 |

**后续：在 5,816 条真实流水线上，这条规则又错了一次。**

用 CRD-7 的语料体检时统计了 19,688 个 job：

| main_df 数量 | job 数 | 占比 |
|---|---|---|
| 恰好 1 个 | 16,025 | 81.4% |
| **0 个** | **2,779** | **14.1%** |
| 多于 1 个 | 884 | 4.5% |

"至少有一个"依然会让 14% 的合法 job 判死。最后降级成 warning，
具体哪几个完全交给文档比对。

**同一条规则改了三次，每次都是同一个病。**
第一次"恰好一个"，第二次"至少一个"，第三次才承认
——"有没有"只能由输入文档决定，不能由校验器假设。

**留下的规则**：

> 校验器里每一条硬约束，都要能回答："这是规范，还是我的习惯？"
> 答不出来就降级成 warning，交给文档逐项比对。

### 3.11 阶段 10：盲区审计 —— 校验器报 1.0，产物丢 14 个字段

**触发**：有人问了一句"你是不是没做幻觉处理"。

**注意这里的查法变了**：不是看校验器说什么，而是**看它没说什么**。

**动作**：写一个脚本，把源文件和产物**逐键展开**成扁平的键值对，直接比。

```
源 50 个键值，缺/不同 14 个
  extract.connections.alias        源=SALES_LANDING    产物=缺失
  extract.connections.keyName      源=SURROGATE_KEY    产物=缺失
  extract.connections.requestFlags 源={'includeDeleted': False}  产物=缺失
  load.connections.alias / tableSpace / numPartitions / flipAlias ...
```

而报告上写着 `grounding = 1.000`，`violations = []`。

**根因不在模型，在文档。** 这 9 类字段从来没进设计文档：

| 层级 | 文档缺的字段 |
|---|---|
| `extract.connections` | `alias`、`keyName`、`requestFlags` |
| `load.connections` | `alias`、`tableSpace`、`numPartitions`、`flipAlias`、`connector`、`credentials` |

校验器拿文档当"应该长什么样"的标准。**文档没写的，它不会要求；不会要求，模型丢了也不算错。**

**修正的第一步**：把字段补进文档。然后一个连一个地暴露新问题：

| 补完 | 暴露的新问题 |
|---|---|
| 文档加 `Conn Alias` / `Key Name` / `Flags` | 模型开始写，但没有规则比对 |
| 加 `S_EXTRACT_PARAMS` | 发现 `nullAble` / `dataTypeArgs` 从来没比过 |
| 加 `S_COL_NULLABLE` / `S_COL_PRECISION` | 发现整段 load 消失会被 `continue` 跳过 |
| 加 `S_LOAD_MISSING` | 发现 `loadObject` 和 `metadata.name` 被混成一列 |
| 加 `S_SIZE` | 发现 `setups.size` 从来没比过 |

**其中"整段 load 消失"最典型**：

```python
if j is None or j.load is None:
    continue      # ← 没有写入就不检查
```

模型把 JDBC 那段连接整段删掉，报告仍然是 1.0。
**"没有东西可检查"被当成了"检查通过"。**

**留下的规则**：

> 校验器只能校验文档里有的东西。**文档的盲区就是裁判的盲区。**
> 而"缺失"必须显式报错，不能因为"没东西可查"就跳过。

### 3.12 阶段 11：提示词的形状变成产物的形状

补字段的过程中，模型连续犯了三个"看起来完全合理"的错，每一个都源自**我怎么写需求**。

**(1) 一行 key=value 被摊平**

prompt 里写：

```
load: object=X metadata_name=X query=Y mode=overwrite connector=cos credentials=demo-cos
```

模型照抄成：

```yaml
load:
  objectName: X
  query: Y
  connector: cos        # ← 应该在 connections[0] 下面
```

解析器只读 `load.connections[0].connector`，于是整段写入静默消失。

改成缩进块 + JSON 描述连接，一次就对：

```
load:
  connections[0]: {"query": "Y", "connector": "cos", ...}
```

**(2) 内部字段名被照抄**

prompt 写 `nullable=false`，模型就写 `nullable: false`。
而 YAML 的键叫 `nullAble`，解析器只认后者——字段静默丢失。

这和阶段 5 的 `partition_by` 是**同一个病第三次发作**。

**(3) 展示用的字段被当成数据**

`partition: false` 是 Landing 表给人看的展示列，不是 schema 的键。
prompt 里带上它，模型就给每一列都写了一遍——29 个列多出 29 行不存在的字段。

**统一结论**：

> **模型不会"理解"你的意图，它会复现你给的结构。**
> prompt 里的形状、键名、嵌套层级，最后都会变成产物的形状。

**检查方法很简单**：把 prompt 打印出来，看它长得像不像你想要的 YAML。

### 3.13 阶段 12：闭环 —— 143 个键值零差异

**动作**：再跑一次 `pdc build`（留一法）。

```
status=passed  rounds=3  tokens=162,500  latency=47.1s

连接级键值：源 143 个，缺/不同 0 个
文本差异：60 行，全是空行、键序、引号风格
```

**完整评测**：

```
[PASS] dim-product-family        2 轮   23k
```

### 3.15 三步定位法：问题到底出在模型、文档、还是裁判

这套方法比任何单条结论都有用。

```
第一步  产物 vs 源文件  →  看"它做错了什么"
第二步  文档 vs 源文件  →  看"我有没有告诉它"
第三步  注入 vs 校验器  →  看"我能不能发现"
```

**问题归属判据**：

| 现象 | 判据 | 归属 | 修哪里 |
|---|---|---|---|
| 产物缺字段，文档里有 | 文档有 | **模型** | prompt / 示例 / 错误信息 |
| 产物缺字段，文档里也没有 | 文档没有 | **文档** | 补列 + 补读取 + 补比对 |
| 产物对，校验器报错 | 源文件也报错 | **裁判过严** | 降级为 warning 或移出 |
| 产物错，校验器不报 | 注入能通过 | **裁判过松** | 加比对规则 |
| 模型改不动同一个错 | 错误信息里没有 YAML 键名 | **反馈** | 改措辞 / 加位置 |
| 模型不调工具、或原地打转 | 上下文里缺少必要信息 | **上下文** | 保留策略 / 摘工具 |

**这张表的用法**：出了问题时，先填"现象"和"判据"两列，
不要凭感觉改 prompt。**六次里有五次，改的不是模型那一侧。**

第一步和第二步都可以用同一条命令完成：

```bash
uv run python -m eval.fidelity 源.yaml 产物.yaml   # 产物 vs 源文件
uv run python -m eval.fidelity 源.yaml 读回的.yaml  # 也可以比"读回的产物"
```

### 3.16 如果你要从零做一遍

按这个顺序做，能省掉我踩的大部分坑。

**第 1 步：写裁判（半天）**

- 结构检查：能不能解析、必需字段在不在
- 契约检查：列名 / 类型 / 可空 / 精度 / 写入目标 / 模式
- 安全检查：明文密钥、越权路径

> 为什么先做这个：没有裁判，你无法判断后面任何一次改动是变好还是变坏。

**第 2 步：写"读输入"，并立刻自检（半天）**

```
输入 → 结构化需求 → 拿需求核对原始输入 → 必须 0 违规
```

> 为什么：读输入丢字段，是所有"模型不行"误判里最常见的一种。

**第 3 步：写循环，门禁先于 prompt（半天）**

- `finish` 时重新校验，不过就驳回并附完整错误清单
- 循环退出条件是 `passed`，不是"模型不调工具了"
- 连续 3 轮同一组错误 → 强制整篇重写

**第 4 步：注入测试，证明检测器会响（1 小时）**

四类各来一次：编造 / 遗漏 / 失真 / 越权（偷偷修上游）。

**第 5 步：留一法评测（2 小时）**

- 参考示例里**不能有**当前用例
- 指标必须有 `exact_match_rate`，且必须为 0

**第 5.5 步：先拿 100 条真实语料体检校验器（半天，最容易被跳过）**

把校验器跑在真实语料上，统计**阻断率**。如果超过 10%，说明规则比现实严格。

我在 5,816 条真实流水线上跑出过这些：

| 现象 | 根因 | 教训 |
|---|---|---|
| 进程崩溃 | `schema: Template` 是字符串，被当列表遍历 | 校验器不能假设形状 |
| 36% 文件被判死 | 要求每个连接都有 `query`，但 box 用 `file_name` | 连接器字段不统一 |
| 14% 的 job 被判死 | 要求必须有 `main_df` | 规则来自归纳 |
| 27% 的 eid 被判死 | 要求 eid 必须声明 schema | 一半语料靠推断 |

**只跑这几个样例，这些一个都发现不了。**

**第 6 步：逐键审计（1 小时，最重要）**

```bash
uv run python -m eval.fidelity 源.yaml 产物.yaml
# 源 201 个键值，缺/不同 0 个
```

它把两个 YAML 展开成同样的扁平键值对直接比，**不需要知道哪些字段重要**。

> 为什么：指标只能测你想到的东西。这一步测的是**你没想到的东西**。
> 第一次用它，就在"校验器报 1.0"的产物上找出 14 个丢失字段。

**第 7 步：改裁判后，用旧产物回测（10 分钟）**

> 为什么：确认标准是变严了，而不是变松了。

**第 8 步：把错误信息当产品做（持续）**

每条必须是：**YAML 键名 + 位置 + 期望值 + 一句为什么**。

**第 9 步：上下文瘦身时，占位符不要放原字段位**

> 为什么：模型会模仿它看到的上一次参数。

**第 10 步：补字段要端到端**

```
模型 → 解析器 → 文档 → 读回 → 比对 → prompt
```

六处缺一处，字段就静默丢失，而报告依然是满分。

## 4. 幻觉治理：五步

### 4.1 第一步：先定义"什么算幻觉"

不定义就没法检测。这个项目里，"幻觉"被拆成四类，因为它们的检测手段完全不同：

| 类型 | 定义 | 例子 | 危险度 |
|---|---|---|---|
| **编造** fabrication | 文档里没有，模型写上了 | 多一个列名、多一个连接器 | 中（跑起来会报错） |
| **遗漏** omission | 文档里有，模型没写 | 少一列、少一个 `mapColumns` | **最高（静默丢数据）** |
| **失真** distortion | 写了，但值不对 | 类型写成 `DecimalType` 少了精度、mode 写反 | 高 |
| **越权** overreach | 超出任务范围的动作 | 偷偷"修好"上游的 schema 漂移 | 高（伪装成负责） |

**为什么遗漏最危险**：编造会炸，遗漏不会。
少一列数据，流水线照跑，三个月后对账才发现。
所以在本项目的裁判里，**遗漏和编造都是 error，但遗漏的提示语写得更重**。

### 4.2 第二步：预防（写 prompt 之前先把路堵死）

| 措施 | 实现 | 为什么有效 |
|---|---|---|
| 只给必需工具 | 6 个工具，`yamlgen.BuildTools` | 每多一个工具，选错概率就高一次 |
| 事实只能来自文档 | 需求文本里没有的，明令禁止 | 减少"合理推测"的空间 |
| 列契约逐字复制 | prompt 里写"不要顺手规范化" | 模型的默认行为是"美化"，必须明确禁止 |
| 示例只给结构 | `read_example` 只读 220 行 | 避免整篇抄（第 5.1 节） |

**预防只能降低概率，不能消除。** 所以真正的治理在下一步。

### 4.3 第三步：检测（四层，全部确定性）

```
第一层  结构   spec_validator
        能不能解析 / kind 对不对 / size 合法吗 / main_df 唯一吗
        → 这一层过不了，后面都不用谈

第二层  契约   spec_validator
        列名格式 / 类型有没有 / 重复列 / 凭证 / 明文密钥 / 越权路径

第三层  语义   spec_grounding（结构化输入）
        文档要求的 job/extract/列/类型/变换参数/写入目标/分区/模式
        逐项比对，漏和编分开报

第四层  归因   spec_grounding.check_text（自由文本输入）
        产出里每个实体标识符，必须在原文里字面出现过
```

每一层返回的都是 `code + message + fix + severity`：

```json
{
  "code": "S_TRANSFORM_PARAMS",
  "message": "eid.RenameColumns: 缺参数 ['mapColumns']（语义丢失 = 能解析但跑不对）",
  "severity": "error",
  "where": "eid"
}
```

**`code` 是稳定的，`message` 是给人看的。** 模型靠 code 定位，人靠 message 理解。

第四层是给自由文本输入准备的。它不是"更弱的第三层"，是**不同性质的检查**：
结构化文档能逐字比对，而 Confluence 导出的一页 md 里根本没有精确列清单，
强行要求精确匹配只会逼模型编一个清单来满足校验器。

### 4.4 第四步：门禁（模型说完了不算完）

```python
def finish(self, summary: str = "") -> dict:
    check = self.validate_yaml()
    if not check["passed"]:
        self.rejected_finishes += 1
        return {"accepted": False, "reason": "校验未通过，不能结束。", "remaining": check}
    self.finished = True
    return {"accepted": True}
```

三个细节：

1. **`finish` 会重新跑一次校验**，不是相信上一次的结果。
2. **驳回时把完整错误清单退回去**，模型下一轮直接照着改，不用重新探索。
3. **循环的退出条件是 `tools.finished`**，不是"模型没有 tool_calls"。

第 3 点很关键：很多实现把"模型不再调工具"当成结束。
在本项目里那意味着模型放弃了，产物可能是错的——不能算完成。

### 4.5 第五步：兜底与降级

| 情况 | 处理 |
|---|---|
| 结构校验失败 | 不做事实对齐（没解析成功，对齐没有意义） |
| 事实对齐没跑 | **grounding 记 0，不记 1**（见 6.6 节，这是上线前抓到的假通过） |
| 轮数用完仍未通过 | 返回 `status=failed`，草稿留在磁盘但**标记未交付** |
| 预算超限 | 立即中止，返回已花的 token |
| 同一组错误连续 3 轮 | 注入"换策略"提示，整篇重写 |
| 连续读示例超过 4 次 | 把 `read_example` 从工具 schema 里摘掉 |

最后一条值得单说。最初的做法是"超过上限就返回错误"，实测**模型又调了 10 次**
——它会把"工具报错"理解成"这次没读到，再试一次"。把工具从 schema 里删掉，
它才会换路。**护栏要改变可选空间，不能只是拒绝。**

## 5. 真实遇到的 11 个问题

按发生顺序记录。每条都写清"现象 → 根因 → 修法 → 面试怎么讲"。

### 5.1 模型把参考答案抄了一遍

**现象**：第一次跑评测，4 条样例全部满分。
但我 diff 了一下产物和源文件——**逐字节相同**。

**根因**：参考示例目录 `samples/pipelines/` 里就包含这条样例的源文件。
模型调 `list_examples` 看到了它，`read_example` 读回来，原样提交。

**这不是模型能力强，是评测污染（data leakage）。** 而且它极难发现：
所有指标都是满分。

**修法**：评测改成**留一法**。生成 A 时，示例目录里只有 B/C/D。
指标里加一条 `exact_match_rate`——**必须为 0，不为 0 就说明还在抄**。

**面试怎么讲**：
> "我第一版评测全满分，一看产物和源文件一模一样。模型把参考答案抄了。
> 改成留一法之后 pass rate 从 100% 掉到真实水平，但那个数字才是能拿出去说的。"

### 5.2 校验器太弱：合法但语义丢失的 YAML 被判通过

**现象**：模型生成了一份完全合法的 YAML，校验器说通过。
我 diff 之后发现：`RenameColumns` 的 `mapColumns` 整段没了、
`Select` 的 `columns` 没了、`JoinByExpression` 的 `columnsToSelect` 没了。

**为什么危险**：`mapColumns` 是 `ORDER_LINE_ID → ORDER_LINE_NUMBER` 的唯一来源。
映射没了，schema 里引用的新列名在数据帧里根本不存在。
**YAML 能解析，跑起来必错。**

**根因**：校验器只检查"列名集合对不对"，不检查"变换有没有把列造出来"。
`transformType` 还在，所以 `S_TRANSFORM_MISSING` 不会触发。

**修法**：加参数级比对。

```python
# spec_grounding.check
for t in spec.transforms:
    cands = [x for x in j.transforms if x.transform_type == t.transform_type]
    if any(_params_match(t.params, x.detail) for x in cands):
        continue
    → S_TRANSFORM_PARAMS
```

修完再拿之前"通过"的那份 YAML 去跑，**新增 21 条违规，其中 9 条是漏列**。

**面试怎么讲**：
> "校验器第一版只看列名集合，模型生成了完全合法但把重命名映射丢光的 YAML，
> 它判了通过。加了参数级比对之后，同一份文件多出 21 条违规。
> 这件事让我明白：**'能解析'和'能跑'是两件事，校验器必须校验后者。**"

### 5.3 文档本身是有损的（反向测试才暴露）

**现象**：修好校验器之后，`spec.params` 还是空的——因为**设计文档里就没有这些参数**。

原来的 `build_transform_chain` 是这么写的：

```python
detail = ", ".join(f"{k}={v}" for k, v in t.detail.items() if not isinstance(v, (dict, list)))
```

为了人类可读，**所有 dict / list 参数被丢掉了**。而 `columns`、`mapColumns`、
`columnsToSelect` 恰恰全是 list/dict。

**根因**：正向（YAML→文档）时，丢掉的参数不影响阅读，所以一年没被发现。
反向（文档→YAML）一跑，立刻暴露。**这就是双向一致性测试的价值。**

**修法**：`Transform Chain` 增加一列 `Params`，存完整 JSON。
`Detail` 保留人类可读版本。**一列给人，一列给机器。**

**面试怎么讲**：
> "我做反向生成的时候发现，设计文档本身丢了变换参数。
> 原因是渲染时为了可读性把 dict/list 过滤掉了。
> 正向永远发现不了这个问题，因为人看不出来少了个映射。
> **单向的测试只能证明单向的正确。**"

### 5.4 校验器太严：把"忠实实现"判成错

**现象**：模型生成的 YAML 里，`eid` job 的 schema 少声明了 7 列。
校验器报 `E_SCHEMA_DIFF`，阻断，8 轮都过不了。

**根因**：这 7 列漂移**是源文件里本来就有的缺陷**（样例故意保留的真实缺陷）。
设计文档里甚至专门有一张 `Schema Diff` 表记录它。
模型忠实实现了文档，却被要求"比输入更正确"。

**这里有一个真正的治理冲突**：

| 选项 | 后果 |
|---|---|
| 强制修好 | 模型必须加一列或删一列 → **那是编造** |
| 放行但记录 | 产物保留了已知缺陷，需要人工决策 |
| 直接判失败 | 任务在输入有缺陷时永远不可能完成 |

**修法**：把 `schema_diff` 从"生成门禁"移到"设计评审"。
生成方向的校验器只回答一个问题：**你有没有忠实实现这份文档。**

> **校验器只能校验你真正要求的东西。**
> 要求"忠实实现"就不能同时要求"比输入更正确"。

**面试怎么讲**：
> "我一开始把 schema 一致性也放进生成门禁，结果模型永远过不了——
> 因为输入文档本身就记录着 7 列漂移。要么它偷偷改，要么它永远失败。
> 这两个都不是我想要的。所以我把这一项移回设计评审：
> **生成任务只对'忠实'负责，不对'正确'负责。**"

### 5.5 校验器自己崩了

**现象**：模型生成的 YAML 少了一个 `transformType`，校验器抛 `KeyError`，
整个进程挂掉，模型只看到 500。

**根因**：`parse_pipeline` 里直接 `raw["jobType"]` / `raw["transformType"]`。
源文件永远有这些字段，所以从来没崩过；模型会漏。

**修法**：两处。

1. 解析器把 `KeyError/TypeError` 转成带位置的 `PipelineParseError`：
   `第 2 个 job 结构不完整（KeyError: 'jobType'）`
2. 校验器外层再兜一层 `except Exception`，返回 `E_PARSE_SEMANTIC`。

**原则**：**校验器的职责是报告错误，不是崩溃。**
它崩了，模型学不到任何东西，只会重试同样的错误。

### 5.6 错误信息用了内部字段名，模型 8 轮改不对

**现象**：只剩一条违规 `partitionBy` 缺失。模型连续 8 轮、烧掉 50 万 token，
就是改不对。

**根因**：错误信息写的是 Python 属性名 `partition_by`。
YAML 里的键叫 `partitionBy`，而且必须写在 `load.connections[0]` 下面。
模型知道"少了个分区"，但不知道往哪儿放。

**修法**：错误信息改成可直接照做的写法：

```
datamart-parquet: 在 load.connections[0] 下写 partitionBy: ['SK_ORDER_DATE']，当前是缺失
```

改完之后：**2 轮通过，76k token**。

**对比**：

| 版本 | 轮数 | token | 结果 |
|---|---|---|---|
| `partition_by 应为 [...]` | 8（上限） | 514,858 | 失败 |
| `在 load.connections[0] 下写 partitionBy: [...]` | 2 | 76,809 | 通过 |

**面试怎么讲**：
> "同一个错误，模型 8 轮改不对。我以为是模型能力问题，
> 后来发现是我的错误信息用了 Python 字段名，而 YAML 里叫另一个名字。
> 改了一句话，2 轮就过了。**Agent 的效果有一半取决于工具反馈的质量，
> 不取决于模型。**"

### 5.7 上下文瘦身把模型带沟里

**现象**：一次失败运行烧掉 **90 万输入 token**。原因是每轮模型都整篇重写 YAML，
历史里堆着 8 个完整版本。

**修法**：`write_yaml` 的正文不进消息历史，只留字符数。

**踩的坑**：第一版占位符写成 `{"text": "<已提交 11955 字符...>"}`。
模型下一轮**把这个占位字符串当成自己的 YAML 又提交了一遍**，
校验器报"YAML 无法解析"，连续 8 轮卡死。

**正确做法**：占位符不能放在原字段位置上。

```python
return {"__omitted__": len(text), "__note__": "上一轮正文已保存，不要复用这个参数对象"}
```

**根因**：模型会模仿它看到的**上一次工具调用参数**。
你把占位符放在 `text` 里，它就把占位符当 `text`。

**这条可以直接当面试题答**：
> "上下文压缩不是把字删掉就行。我第一版把 YAML 替换成一个占位字符串，
> 模型把占位符原样提交回来了。**压缩后的内容仍然是模型的模仿对象。**"

### 5.8 在"看示例"里打转，一次都不写

**现象**：某次运行 34 步，`read_example` 调了 36 次，`write_yaml` 0 次。

**根因**：我当时为了省 token，只保留最新一次示例，把旧的擦掉。
模型发现"上一个示例消失了"，就回头再读；读回来又把新的擦掉——**振荡**。

**修法**：

1. 保留最近**两次**示例（当前参照 + 上一条对照）
2. 累计 4 次后把 `read_example` 从 schema 里摘掉

**教训**：**上下文管理本身会改变模型行为。**
你不是在"删字"，你是在改变它看到的世界。

### 5.9 校验器把自己的假设当成了规范

**现象**：完整的 4 条留一法评测跑完，`pass_rate = 0.75`。
`fact-inventory-snapshot` 连续 5 轮、烧掉 34 万 token，卡在 `E_MAIN_DF`：

```
job eid 有 2 个 main_df: true
```

**根因**：这个样例里有**两个事实源**（库存快照 + 库存调整），
两个都标了 `main_df: true`，后面 join 在一起。
而我的校验器里写着一条规则：**每个 job 有且只有一个主数据集**。

这条规则是我从另外三个样例里总结出来的。写进裁判的那一刻，
它就从"观察"变成了"硬约束"。

**这是 4.4 的同一个病，第二次发作。** 区别只是上次是 schema 规则，这次是 main_df 规则。

**修法**：只检查"至少有一个"，具体哪几个交给文档逐项比对（`S_MAIN_DF`）。

| | 修之前 | 修之后 |
|---|---|---|
| pass_rate | 0.75 | **1.00** |
| 失败用例 | 卡在 `E_MAIN_DF` | 1 轮通过 |

**面试怎么讲**：
> "我的校验器有一条'每个 job 只能有一个主数据集'，结果一条真实流水线有两个
> fact 源，直接卡死。这条规则是我从三个样例里总结的——**我把观察当成了规范**。
> 后来改成只检查'有没有'，具体哪几个交给文档比对。
> 校验器里每一条硬约束，都要能回答'这是规范还是我的习惯'。"

### 5.10 校验器报 1.0，但产物丢了 14 个字段

**这次是别人问我"你是不是没做幻觉处理"，我才去查的。**
查法不是看校验器说什么，是**拿产物和源文件逐键比对**——看校验器没说什么。

**现象**：

```
连接级键值 50 个，缺/不同 14 个
  extract.connections.alias      源=SALES_LANDING   产物=None
  extract.connections.keyName    源=SURROGATE_KEY   产物=None
  extract.connections.requestFlags 源={'includeDeleted': False} 产物=None
  load.connections.alias / tableSpace / numPartitions / flipAlias ...
```

而报告里写着 `grounding = 1.000`，`violations = []`。

**根因不在模型，在文档。** 这 9 类字段**根本没有进设计文档**：

| 层级 | 文档缺的字段 |
|---|---|
| extract.connections | `alias`、`keyName`、`requestFlags` |
| load.connections | `alias`、`tableSpace`、`numPartitions`、`flipAlias`、`connector`、`credentials` |

校验器拿文档当"应该长什么样"的标准。**文档没写的，它不会要求；
不会要求，模型丢了也不算错。**

> **校验器只能校验文档里有的东西。文档的盲区就是裁判的盲区。**

**修法**：把字段补进文档，再补比对规则。这一步连着一个坑：

| 补完 | 暴露的新问题 |
|---|---|
| 文档加 `Conn Alias` / `Key Name` / `Flags` | 模型开始写，但没有规则比对 |
| 加 `S_EXTRACT_PARAMS` | 发现 `nullAble` / `dataTypeArgs` 从来没比过 |
| 加 `S_COL_NULLABLE` / `S_COL_PRECISION` | 发现整段 load 消失会被 `continue` 跳过 |
| 加 `S_LOAD_MISSING` | 发现 `loadObject` 和 `metadata.name` 被混成一列 |

**最终结果**：

```
源 143 个键值，缺/不同 0 个
文本差异 60 行，全是空行、键序、引号风格
```

**面试怎么讲**：
> "我的校验器报满分，但我拿产物和源文件逐键比，发现 14 个字段没写。
> 不是模型偷懒，是设计文档里根本没有这些列。
> 我补了 9 类字段和 5 条比对规则，143 个键值做到零差异。
> **这件事让我明白：幻觉治理的上限不是模型，是你能描述出来的契约。**"

### 5.11 提示词的形状会变成产物的形状

补字段的过程中，模型连续犯了三个"看起来完全合理"的错，每一个都源自**我怎么写需求**。

**(1) 一行 key=value 被摊平**

原来 prompt 里写：

```
load: object=X metadata_name=X query=Y mode=overwrite connector=cos credentials=demo-cos
```

模型照抄成：

```yaml
load:
  objectName: X
  query: Y
  connector: cos        # ← 应该在 connections[0] 下面
```

解析器只读 `load.connections[0].connector`，于是整段写入静默消失。
改成缩进块 + JSON 描述连接后，一次就对：

```
load:
  connections[0]: {"query": "Y", "connector": "cos", ...}
```

**(2) 内部字段名被照抄**

prompt 写 `nullable=false`，模型就写 `nullable: false`。
而 YAML 的键叫 `nullAble`，解析器只认后者——字段静默丢失。
这和 4.6 的 `partition_by` 是**同一个病第三次发作**。

**(3) 展示用的字段被当成数据**

`partition: false` 是 Landing 表给人看的展示列，不是 schema 的键。
prompt 里带上它，模型就给每一列都写了一遍——
29 个列多出 29 行不存在的字段。

**统一结论**：

> **模型不会"理解"你的意图，它会复现你给的结构。**
> prompt 里的形状、键名、嵌套层级，最后都会变成产物的形状。

**这一条比任何 prompt 技巧都值钱。** 检查方法也很简单：
把 prompt 打印出来，看它长得像不像你想要的 YAML。

## 6. 测试怎么做的（全过程）

这一节按"怎么长出来的"写，不是按教科书分类写。

因为测试的难点从来不是"知道要测什么"，而是：

> 你写的第一版测试，大概率测的是**你以为的代码**，不是**真实的代码**。

---

### 6.0 先定两条原则

**原则一：不联网的测试和联网的测试必须分开**

```
CI（每次 push 都跑）      198 个测试，3.7 秒，0 元
手动（改完 prompt 才跑）   真实模型评测，90 秒，约 $0.08
```

混在一起的后果：模型今天状态差，你以为是代码坏了；
或者为了省 CI 时间，把关键断言删了。

**原则二：每一个检查，都要有一条"证明它会响"的测试**

检测器不报警，可能是"没检测到问题"，也可能是"检测器坏了"。
这两件事在日志里长得一模一样。

所以每加一条规则，必须同时加一条**故意触发它**的测试。
这和 3.3 节的注入审计是同一个思路，只是从手工做成了自动化。

---

### 6.1 测试是怎么长出来的：161 → 198

测试不是一次写完的，是**每出一次事故，加一条**。

| 时间点 | 数量 | 当时加了什么 | 为什么必须加 |
|---|---|---|---|
| build 开工前 | 161 | design 方向的全部测试 | 已有功能不能退化 |
| 写完裁判 | ~175 | 结构错误 7 类、注入 4 类、读文档保真 | 裁判先自证 |
| 写完循环 | ~189 | 门禁、卡住检测、兜底、预算、示例上限 | 控制流不能靠人盯 |
| `E_MAIN_DF` 事故后 | 190 | `test_two_main_df_is_legal` | 锁住"规则不能来自归纳" |
| 连接级契约后 | 195 | nullable / 精度 / load 参数 / size / 整段 load 缺失 | 锁住文档盲区 |
| 加入 fidelity 后 | 198 | 忠实拷贝 / 漂移 / 编造 | 工具本身也要测 |

**注意最后三条**：它们不是"功能测试"，是**事故的化石**。
每一条对应一个真实发生过的错误，注释里写着那次事故。

> 测试的价值不在于覆盖率，在于**同样的错不会犯第二次**。

---

### 6.2 第一层：裁判的测试（改一个字符）

**做法**：准备一份合法 YAML，每次只改一个地方，断言报出对应的 code。

```python
@pytest.mark.parametrize(
    ("mutate", "expected"),
    [
        (lambda s: s.replace("kind: DimensionPipeline", "kind: Something"), "E_KIND"),
        (lambda s: s.replace("        size: S\n", ""), "E_SIZE"),
        (lambda s: s.replace("        size: S", "        size: HUGE"), "E_SIZE_VALUE"),
        (lambda s: s.replace("          main_df: true\n", ""), "E_MAIN_DF"),
        ...
    ],
)
def test_validator_catches_structural_errors(mutate, expected: str) -> None:
    assert expected in codes(mutate(BASE))
```

**为什么用"改一个字符"而不是"从零写一个错误文件"**：

从零写，你没法确定错误是哪一个字段引起的——三个错一起报，
测试通过了也不代表第三条规则有效。**一次只改一个变量**，
才能把"测试通过"归因到"这条规则生效"。

**这一层覆盖的 7 类**：

| 变异 | 期望 code | 真实含义 |
|---|---|---|
| `kind` 改掉 | `E_KIND` | 顶层类型不对 |
| 删掉 `setups.size` | `E_SIZE` | 缺必需字段 |
| `size: HUGE` | `E_SIZE_VALUE` | 枚举值非法 |
| 删掉 `main_df` | `E_MAIN_DF` | 没有主数据集 |
| 删掉 `dataType` | `E_COL_TYPE` | 列契约不完整 |
| 复制一列 | `E_DUP_COL` | 重复列 |
| `query: ../` | `W_PATH` | 越权路径 |
| 明文密码 | `E_SECRET` | 密钥泄漏 |

**还有一个"不崩"的测试**：

```python
def test_validator_reports_semantic_structure_problem():
    broken = BASE.replace("    - jobType: eid\n", "    - \n")
    issues = validate_text(broken)
    assert {i.code for i in issues} == {"E_PARSE_SEMANTIC"}
    assert "第 1 个 job" in issues[0].message
```

这条测的不是"能不能抓错"，是**"抓错的时候会不会崩"**。
校验器崩了，模型只看到 500，学不到任何东西。

---

### 6.3 第二层：循环的测试（用剧本演模型）

**问题**：循环的正确性（门禁生效、卡住能检测、预算能中止）和模型能力无关，
但真跑一次要 30 秒、几毛钱，而且结果不稳定。

**做法**：`ScriptedLLM` —— 按预设剧本返回，不联网、不花钱、完全确定。

```python
llm = ScriptedLLM([
    LLMReply(tool_calls=[call("write_yaml", text=broken)]),   # 先交一版错的
    LLMReply(tool_calls=[call("validate_yaml")]),             # 自检
    LLMReply(tool_calls=[call("write_yaml", text=BASE)]),     # 改对
    LLMReply(tool_calls=[call("validate_yaml")]),
    LLMReply(tool_calls=[call("finish", summary="ok")]),
])
result = run_build(llm, req, out_dir=tmp_path, examples_dir=tmp_path)
assert result.passed and result.rounds == 2
```

**五个剧本，对应五种真实观测到的模型行为**：

| 剧本 | 断言 | 来自哪次观测 |
|---|---|---|
| 先错后对 | `passed=True`，`rounds=2` | 正常修复路径 |
| 有错就 `finish` | `passed=False`，错误清单被退回 | 门禁必须拒绝 |
| 连续三轮同一组错误 | `stuck_events>=1` | 真实卡死 |
| 把 YAML 贴在正文里 | `passed=True`，trace 有 `safety` | 模型不调工具 |
| 反复读示例 | 第 4 次后工具从 schema 消失 | 34 步 36 次读、0 次写 |

**为什么这层最值钱**：它把"Agent 的行为"变成了**可断言的函数**。
不需要真的等模型犯错，也能证明"犯错时系统会怎么反应"。

**一个细节**：断言要检查**退回给模型的内容**，不只是最终状态。

```python
tool_payloads = [json.dumps(m) for m in llm.calls[-1] if m.get("role") == "tool"]
assert any("accepted" in p and "false" in p for p in tool_payloads)
```

否则你只能证明"没通过"，不能证明"模型知道自己为什么没通过"。

---

### 6.4 第三层：闭环评测（真模型 + 留一法）

**这一层只回答一个问题**：模型在没见过答案的情况下，能不能做对。

```bash
uv run python -m eval.build_eval
```

**留一法的实现**（关键就三行）：

```python
for p in SAMPLES.glob("*.yaml"):
    if p.name == holdout.name:
        continue            # ← 把当前用例从参考示例里摘掉
    (d / p.name).symlink_to(p)
```

**五个指标，各有各的用途**：

| 指标 | 抓什么 | 期望 |
|---|---|---|
| `pass_rate` | 能不能交付 | 越高越好 |
| `avg_rounds` | 反馈质量 | 越低越好 |
| `avg_tokens` | 成本 | 越低越好 |
| `exact_match_rate` | **有没有抄答案** | 必须为 0 |
| `document_loss` | 文档缺陷，不算模型的账 | 单独记录 |

**为什么要跑两遍**：同一份文档，轮数会在 1~3 之间波动。
只报一次最好成绩，是评测里最常见的撒谎方式。

---

### 6.5 第四层：保真审计（不看指标）

```bash
uv run python -m eval.fidelity 源.yaml 产物.yaml
```

这一层不是"测试"，是**审计**。区别在于：
测试检查你写下的断言，审计检查**你没写下的东西**。

它把两个 YAML 展开成扁平键值对直接比，不需要知道哪些字段重要。
第一次用它，就在"所有指标满分"的产物上找出 14 个丢失字段。

**它自己也有三条测试**：

```python
def test_fidelity_reports_zero_on_faithful_copy(...)     # 不误报
def test_fidelity_catches_connection_level_drift(...)    # 漏了能报
def test_fidelity_catches_fabricated_field(...)          # 编了也能报
```

> 工具也要被测。一个永远报 0 差异的审计工具，比没有更危险。

---

### 6.6 测试本身出的 6 个问题

测试代码也会骗人。这一节记录的是**测试的缺陷**，不是产品的缺陷。

第一次跑 `tests/test_build_agent.py`：**5 个失败，4 个是测试写错，1 个是产品错。**

| # | 现象 | 真正的原因 | 归属 |
|---|---|---|---|
| 1 | `E_MAIN_DF` 用例没触发 | 我改的是 `transform`，不是 `main_df` | 测试 |
| 2 | 密钥用例报 `E_PARSE` | 插入的缩进把 YAML 弄坏了 | 测试 |
| 3 | 列缺失用例没触发 | 样例里根本没有 `PRODUCT_FAMILY` 这一列 | 测试 |
| 4 | `TypeError: Step not subscriptable` | 把 dataclass 当 dict 用 | 测试 |
| 5 | 语义结构错误完全没报 | 我删 `_schema_issues` 时把**解析检查**一起删了 | **产品** |

**这张表本身就是结论**：

> **测试红了，先证明是产品错，再改产品。**
> 4/5 的时候，错的是测试。

**另外两个更隐蔽的测试缺陷**：

**(1) 假通过：grounding 报 1.0，其实一次都没查**

结构校验失败时，事实对齐根本没执行，但报告里写了 `grounding=1.0`。
看起来完美，实际什么都没验证。

```python
grounding = score(...) if tools.parsed else 0.0   # 修法
```

> **没执行的检查，不能报"通过"。** 这类假通过比失败危险得多。

**(2) 分母选错，指标反向激励**

对齐率最初的分母是"YAML 里有多少项"。
那样**漏得越多，分母越小，分数越好看**——正好奖励了最危险的行为。
改成"文档要求生成多少项"才对。

> 指标的分母决定了模型会往哪个方向作弊。

**为什么这两类测试没抓到**

| bug | 测试当时断言什么 | 为什么漏 | 后来补的测试 |
|---|---|---|---|
| 假通过 | `result.passed == False` | 断言的是**结论**，不是**证据** | `assert result.grounding == 0.0` |
| 分母 | 一份**完整**的产物 | 只测正常输入，没测退化输入 | `assert expected_items(spec) >= 总列数` |

两条通用的写法：

1. **指标要测"没数据"的状态。** 空列表既可能是"没问题"，也可能是"没检查"，
   这两种情况必须有办法区分。
2. **比率要测分母的边界。** 0 项、1 项、全部缺失，各来一条。

> 只测 happy path 的测试，保护不了 happy path 以外的一切——
> 而事故全都在那里。

---

### 6.7 回归：改了裁判，用旧产物回测

每次改校验器，都拿**之前被判通过的产物**重新跑一遍。

```bash
uv run pytest -q
uv run python -m eval.fidelity samples/pipelines/fact-order-fulfillment.yaml out/fact-order-fulfillment.yaml
```

5.2 节就是这么发现的：同一份"通过"的文件，新校验器报出 **21 条违规，9 条是漏列**。

**这条比任何单测都值钱**：它验证的是"我的标准变严了，还是没有变松"。

**配套纪律**：修完一个 bug，必须加一条锁住它的测试，注释里写清事故。

```python
def test_two_main_df_is_legal() -> None:
    """一个 job 可以有两个主数据集。

    这条用例对应一次真实误判：校验器写了"只能有一个 main_df"，
    结果一条真实的库存流水线（快照 + 调整两个 fact 源 join）永远过不了。
    规则是从三个样例里总结出来的，**我把观察当成了规范**。
    """
```

半年后你看不懂代码，但看得懂这段注释。

### 6.9 故意不测的四件事，以及为什么

先说结论：**不是"做不到"，是"做了会让测试变差"。**

判断一件事该不该测，用四个问题：

```
1. 确定性   同样的输入，会不会得到同样的输出？
2. 归属     坏了，是不是我的代码？
3. 可修性   红了之后，我能不能修？
4. 成本比   维护成本 vs 它抓到问题的概率
```

四条里只要有两条不满足，就不该写成测试——应该写成**度量**或**人工检查**。

| 对象 | 确定性 | 归属 | 红了能修吗 | 结论 |
|---|---|---|---|---|
| 模型输出的措辞 | ❌ | 半 | 能，但会一直红 | 测**属性**，不测文本 |
| 模型本身（能力/知识） | ❌ | ❌ | 不能 | 度量，**不门禁** |
| UI 像素 | ✅ | ✅ | 能 | 成本 > 收益 |
| 100% 行覆盖率 | ✅ | ✅ | —— | 当**诊断**，不当目标 |

下面逐条说清"为什么"和"如果非要做怎么做"。

---

#### (1) 模型输出的措辞

**为什么不做**

同一个输入跑两次，模型写的话不一样：

```
第一次：该列在数据帧中存在，但 load.schema 未声明。
第二次：load.schema 缺少这一列，数据帧里有。
```

如果你 `assert "该列在数据帧中存在" in output`，这条测试**每次都会红**。
红了三次之后，你会做两件事之一：改断言、或者加 `skip`。
两种做法都让测试变成装饰。

**更糟的后果**：一个经常红的测试会训练你忽略红色。
等它真的抓到 bug 时，你也会条件反射地以为"又是它抽风"。

> **一个坏测试比没有测试更糟**，因为它消耗的是你对红色的信任。

**那测什么**

测**属性**（property），不测**值**（value）：

```python
# ❌ 测措辞
assert "该列在数据帧中存在" in output

# ✅ 测属性
assert "SK_ORDER_DATE" in output          # 必须提到这一列
assert "not asserted" not in output       # 不许含糊其辞
assert all(rid in real_rule_ids for rid in cited_rules)   # 引用的规则必须真实存在
```

属性是稳定的，措辞不是。

**如果非要做**：用 LLM-as-judge 打分（"这段话有没有编造"），
但那是**评测**，不是测试——它有方差，不能阻断 CI。

---

#### (2) 模型本身（能力、知识）

**为什么不做**

三个理由，一个比一个硬：

1. **不是我的代码。** 模型是别人的服务，我改不了。
2. **会在我脚下变。** 服务商升级模型，我的测试就红了，而我什么都做不了。
3. **测了也不能指导行动。** 知道"模型这次没做对"之后，我能做的只有改 prompt / 改工具 / 换模型——这些都需要人来判断。

**那做什么**

**度量，不门禁。**

```
不联网的 CI      198 个测试，断言"我的代码对不对"
手动的评测       4 条真实用例，度量"模型这次表现如何"
```

区别在于**红了之后怎么办**：

| | 测试红了 | 评测分低了 |
|---|---|---|
| 含义 | 我写错了 | 模型/数据/prompt 变了 |
| 处理 | 必须修 | 看情况，可以接受 |
| 是否阻断 | 是 | 否 |

**但我测"我如何处理模型的行为"**：

```python
# 模型把 YAML 贴在正文里而不调工具 —— 我的兜底逻辑对不对？
LLMReply(content="```yaml\n...\n```")
assert result.passed

# 模型连续三轮犯同一个错 —— 我的卡住检测会不会触发？
assert result.stuck_events >= 1
```

> **不测模型会不会犯错，测它犯错时我会不会发现。**

---

#### (3) UI 像素

**为什么不做**

这个项目的 UI 是一个单文件 HTML，没有构建步骤，一周改三次。

要测像素，需要：浏览器 + 截图 + 跨机器字体渲染一致 + 基线管理。
这套基础设施的维护成本，比 UI 本身的代码量还大。

更关键的是：**它和这个岗位考的东西无关。**
面试官不会问"你的按钮圆角是 4px 还是 8px"，会问"任务提交后状态怎么同步"。

**那测什么**

测 **UI 依赖的契约**，不测 UI 长什么样：

| 层 | 测法 |
|---|---|
| API 契约 | `POST /runs` 返回 202 + job id；`GET /runs/{id}` 状态流转 |
| 事件流 | SSE 按顺序发出 `step` / `tool` / `final` |
| 错误路径 | 没带 token 返回 401；超出限流返回 429 |
| 人工 | 打开页面点一遍（30 秒） |

**如果非要做**：一条 Playwright 冒烟——登录 → 提交 → 看到结果。
只测这一条主路径，别测样式。**测"能不能用"，不测"好不好看"。**

---

#### (4) 100% 行覆盖率

**为什么不做**

这是最重要的一条，因为它反直觉。

**覆盖率衡量"执行过"，不衡量"验证过"。**

```python
def result():
    grounding = score(...) if parsed else 0.0   # 这一行
    return grounding                            # 这一行
```

这两行在测试里**都执行过**——覆盖率 100%。
但当时没有一条断言检查 `grounding` 的值，所以"没跑检查却报 1.0"这个 bug
在覆盖率报告上**完全是绿的**。

> **6.6 节那两个假通过 bug，代码都被执行过。覆盖率救不了它们。**

**那看什么**

1. **按事故看**：每一个真实发生过的 bug，有没有一条测试锁住它？
2. **按边界看**：外部输入（解析器、API、文档读取）有没有测？
3. **按文件看 0%**：哪个文件一行都没被执行过？那通常是忘了接上，不是"不重要"。

覆盖率当**诊断工具**（"这个文件 0%，我是不是漏了什么"），
不当**目标**（"必须到 90%"）。当目标就会有人写没有断言的测试来刷分。

**如果非要一个数字**：看**关键路径**的覆盖率，不看全局。
这个项目里关键路径是 `spec_validator` / `spec_grounding` / `yamlgen`，
它们接近 100%；`render.py` 的样式分支没人管。

---

#### 一句话总结

> 测试的价值不在"绿的时候好看"，在**"红的时候你信"**。
> 不确定的、不归你的、红了也修不了的，都不该写成测试——
> 写成度量、写成人工检查、或者干脆不写。

**这四件事的替代品，合起来就是一句话**：

| 不测 | 改测 |
|---|---|
| 措辞 | 属性（必须提到某列 / 不许编造） |
| 模型能力 | 行为（犯错时我能不能发现） |
| UI 像素 | 契约（API 状态码、事件顺序） |
| 覆盖率 | 事故（每个 bug 有没有回归测试） |


---

### 6.10 一句话总结这一节

> 不联网的测控制流，联网的测能力。
> 每一条规则都要有"证明它会响"的测试。
> 测试红了，先怀疑测试。
> 修完 bug，加一条锁住它的用例，注释里写清那次事故。


**同一个模型、同一个输入，只改了错误信息的措辞。**
这是整份文档里最有说服力的一组对照。

### 7.3 留一法评测：n=3 的方差

```bash
uv run python -m eval.build_eval --repeat 3
```

| 指标 | 均值 ± 标准差 | 说明 |
|---|---|---|
| pass_rate | **1.00 ± 0.00** | 12/12，一次没失败 |
| avg_rounds | **1.92 ± 0.14** | 单次会在 1.75~2.00 之间跳 |
| avg_tokens | **69,341 ± 13,192** | 波动 ±19%，因为重写次数不同 |
| exact_match | **0.000 ± 0.000** | 留一法生效，没有抄 |

**逐用例轮数（三次）**：

| 用例 | 轮数 | token 区间 |
|---|---|---|
| dim-customer-segment | 1 / 2 / 2 | 5.1 万 ~ 8.1 万 |
| dim-product-family | 3 / 1 / 1 | 1.7 万 ~ 5.2 万 |
| fact-inventory-snapshot | 2 / 2 / 2 | 4.8 万 ~ 7.8 万 |
| fact-order-fulfillment | 2 / 3 / 2 | 7.3 万 ~ 19.0 万 |

**怎么读这张表**：

1. **通过率稳定**，说明机制是可靠的；
2. **轮数有方差**，单次最好的 1 轮不代表下次还 1 轮；
3. **token 波动 19%**，因为每次重写的内容量不同；
4. **n=3 不做显著性声明**——三遍只能看波动范围，不能证明差异。

> 只报一次最好成绩，是评测里最常见的撒谎方式。
> 报 `1.92 ± 0.14`，比报 `1.75`（最好那次）诚实，也更像工程判断。

### 7.4 合约变严之后：同样的通过率，不同的难度

补完连接级契约后重跑，**轮数从 1.5 涨到 2.0**。这是应该的——
要求模型逐字复现 143 个键值，比只复现列名难得多。

| 阶段 | pass_rate | avg_rounds | avg_tokens | exact_match |
|---|---|---|---|---|
| 只比列名（合约松） | 1.00 | 1.50 / 1.75 | 63.9k / 57.4k | 0.000 |
| 比连接级全字段（合约严） | **1.00** | **1.92 ± 0.14** | **69.3k ± 13.2k** | **0.000** |

**为什么两个阶段都要列**：如果只报"4/4 通过"，你看不出合约变严了。
**通过率相同、但难度不同，是两个完全不同的结论。**

### 7.5 成本

| 场景 | token | 约合 |
|---|---|---|
| 一次通过（30 列） | 7.7 万 | ~$0.02 |
| 留一法平均（含重试） | 6.9 万 | ~$0.02 |
| 三遍评测（12 次生成） | 83.2 万 | ~$0.25 |
| 失败到上限（5.6 节） | 51 万 | ~$0.15 |
| 更早的失控版本 | 90 万 | ~$0.26 |

**结论：失败比成功贵 7 倍以上。** 所以"提高一次通过率"不是体验问题，是成本问题。

而提高一次通过率最有效的手段，不是换模型，是**把错误信息写清楚**（5.6 节）。

## 9. 面试问答（按这份文档能答的）

**Q1：你的 Agent 产出了什么？**
> YAML 是模型写的。代码只做两件事：把文档读成结构化需求，和判对错。

**Q2：怎么保证它不瞎编？**
> 四层确定性检查。第一层结构，第二层契约，第三层和文档逐项比对（漏和编分开报），
> 第四层自由文本时要求实体在原文里字面出现。全部是代码，没有模型参与判分。

**Q3：模型说完成了，你怎么知道真完成了？**
> `finish` 工具会重新跑一次校验，不过就驳回，把错误清单退回去。
> 循环的退出条件是校验器通过，不是模型不调工具了。

**Q4：它写错了怎么办？**
> 错误信息带稳定 code 和可直接照做的 fix。模型按 code 改，不重写整篇。
> 同一组错误连续 3 轮，强制整篇重写——局部修补已经证明无效了。

**Q5：你的评测怎么做的？**
> 留一法。生成 A 时示例目录里只有 B/C/D，否则模型直接抄答案。
> 我第一次跑就是全满分，一 diff 发现逐字节相同。指标里专门留了
> `exact_match_rate`，必须为 0。

**Q6：遇到过最难的 bug 是什么？**
> 一个 `partitionBy` 缺失，模型 8 轮改不对。最后发现是我的错误信息写了
> Python 字段名 `partition_by`，而 YAML 里叫 `partitionBy`，还得放在
> `connections[0]` 下。改了一句话，2 轮就过了。
> **Agent 的效果一半取决于工具反馈的质量。**

**Q7：怎么控制成本？**
> 失败比成功贵 7 倍，所以重点是提高一次通过率。
> 另外做上下文瘦身：模型每轮整篇重写，历史里不留全文。
> 这里踩过坑——占位符放在原字段位置上，模型会把占位符当内容提交回来。

**Q8：校验器太严会怎样？**
> 会逼模型编造。我的输入文档里本来就有 7 列 schema 漂移，
> 如果生成门禁要求 schema 一致，模型只能偷偷加一列或删一列。
> 所以我把这一项移回设计评审：**生成只对忠实负责，不对正确负责。**

**Q9：这个和"让 ChatGPT 直接写 YAML"有什么区别？**
> 三个。可判定——有 189 个测试和四层检查，错在哪一行能指出来。
> 可复现——同一份文档跑两次，结构一致。
> 可回归——改了校验器，拿旧产物回测，立刻知道标准变严还是变松。

**Q10：这个项目最大的限制是什么？**
> 文档的信息完整度就是天花板。文档丢了 `keyName`，反推就永远丢。
> 所以我没有做模板渲染器——那会把这个任务变成 workflow，
> 而我想要的正是"产物由模型写、失败无法伪装"这件事。

## 附：一分钟讲完这个模块

> 原来的项目是 YAML 生成文档，产物是代码算的，模型只写叙述。
> 我加了一个反方向：给设计文档，让模型写 YAML。
>
> 关键设计是**裁判先行**：先写确定性校验器，再写生成循环。
> 模型可以随时说"完成了"，但 `finish` 会被校验器驳回。
>
> 治理上分了四层检查，把幻觉拆成编造/遗漏/失真/越权四类——
> **遗漏最危险，因为它不报错**。
>
> 真实踩过的坑：第一版评测全满分，结果是模型把参考答案抄了；
