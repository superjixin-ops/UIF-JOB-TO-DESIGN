# 检索的切分与测试集设计

> 结构切分 → 向量切分 → 测试集。三者的顺序不能反。

> 这份文档回答两个问题：**chunk 怎么切**、**测试集怎么造**。
> 两个问题的共同点：做错了，后面的所有指标都会骗你。

---

## 一、切分：按语义边界，不按行数

### 1.1 三种用途，三种切法

不要用一个 chunk 服务所有场景。这个项目里有三种检索：

| 用途 | 切分单位 | 大小 | 必须带的信息 |
|---|---|---|---|
| **few-shot 示例** | 整条 pipeline（或整个 job） | 100~300 行 | pipeline 名、job 链、规模 |
| **结构检索** | 一张结构卡 | 1 行 | job 链、连接器、变换类型 |
| **文档 RAG** | 一个 `##` 小节 | 200~500 token | 文件、标题路径 |

给 few-shot 一篇 600 行的 YAML 是浪费；给文档 RAG 一整条 pipeline 是噪音。

### 1.2 pipeline YAML 怎么切

**按 job 切，不按行切。**

一条 600 行的 pipeline 通常有 3~4 个 job，每个 job 是一个完整单元：

```
pipeline/fact-order-fulfillment
├── meta                    apiVersion / kind / metadata / owner
├── job[0]                  eid（extract + transform + load）
├── job[1]                  datamart-parquet
└── job[2]                  datamart-self-serve
```

单个 job 太大时（>300 行），再按三段切：

| chunk | 内容 | 为什么单独切 |
|---|---|---|
| `job[0]/extract` | 数据源、连接器、凭证、query | 回答"数据从哪来" |
| `job[0]/transform` | 变换序列、参数 | 回答"怎么处理" |
| `job[0]/load` | 目标表、schema、分区 | 回答"写到哪、什么契约" |

**但每个 chunk 必须带血缘锚点**：

```yaml
# chunk: pipeline=fx, job=eid, section=transform
jobType: eid
objectNames: [ORDER_LINES]      # 上游
aliasResult: ORDER_LINES        # 下游
```

缺了 `objectNames` / `aliasResult`，这个 chunk 就孤立了——模型看到一串变换，
不知道数据从哪来、到哪去。

### 1.3 六条硬规则

| # | 规则 | 反面例子 |
|---|---|---|
| 1 | 按语义边界切（job / `##` 标题 / 表格） | 按 50 行切，把一个 transform 列表劈成两半 |
| 2 | 每个 chunk 自包含 | 只存 `- transformType: Drop`，不存它属于哪个 job |
| 3 | 带完整路径 | `chunk_id = pipeline/job/section` |
| 4 | 不跨块 | 一个 YAML block 不能被切开 |
| 5 | 代码块 / 表格整体保留 | 把 markdown 表格从中间切开 |
| 6 | 重叠只在长文里用（10~15%） | YAML 不需要重叠，重叠只会造成重复召回 |

### 1.4 一个具体的切分示例

原始（截断）：

```yaml
- jobType: eid
  extract:
    - alias: ORDER_LINES
      main_df: true
      connections:
        - credentials: demo-cos
          connector: cos
          query: landing/orders/order_lines/transform.parquet
  transform:
    - transformType: RenameColumns
      objectNames: [ORDER_LINES]
      mapColumns: {ORDER_LINE_ID: ORDER_LINE_NUMBER}
      aliasResult: ORDER_LINES
  load:
    metadata: {name: FACT_ORDER_FULFILLMENT}
    connections:
      - mode: overwrite
        loadObject: FACT_ORDER_FULFILLMENT
        partitionBy: [ORDER_DATE]
    schema:
      - {columnName: ORDER_FULFILLMENT_KEY, dataType: IntegerType, nullAble: false}
```

切成 3 块，每块都带 `jobType` 和锚点：

```yaml
# chunk_id: fact-order-fulfillment/eid/extract
jobType: eid
extract:
  - alias: ORDER_LINES
    main_df: true
    connections: [{credentials: demo-cos, connector: cos,
                   query: landing/orders/order_lines/transform.parquet}]
```

```yaml
# chunk_id: fact-order-fulfillment/eid/transform
jobType: eid
inputs: [ORDER_LINES]
output: ORDER_LINES
transform:
  - transformType: RenameColumns
    mapColumns: {ORDER_LINE_ID: ORDER_LINE_NUMBER}
```

```yaml
# chunk_id: fact-order-fulfillment/eid/load
jobType: eid
inputs: [ORDER_LINES]
load:
  metadata: {name: FACT_ORDER_FULFILLMENT}
  connections: [{mode: overwrite, loadObject: FACT_ORDER_FULFILLMENT,
                 partitionBy: [ORDER_DATE]}]
  schema: [...]
```

### 1.5 切分质量怎么验（不花钱）

切完先跑四个硬门禁，任何一个不过就不许进检索评测：

| 检查 | 方法 | 通过线 |
|---|---|---|
| **结构完整** | YAML chunk 能否独立解析 | 100% |
| **路径完整** | 每个 chunk 有 `pipeline/job/section` | 100% |
| **答案覆盖** | 测试集里每个 gold 答案完整落在某个 chunk 内 | 100% |
| **重叠率** | 相邻 chunk 的 token 重叠 | < 20% |

第三条最容易被忽略：如果标准答案跨了两个 chunk，召回永远算不对，
而你可能会误以为是"检索效果差"。

## 二、向量的切分：一个 chunk 到底是什么

### 2.1 一句话定义

> **一个 chunk = 一次 embedding 的输入 = 检索返回的最小单位。**
> 它必须同时满足三个条件：**自包含、单主题、可引用**。

这句话决定了后面所有取舍。因为向量是"一个点"，一个点只能代表一个意思。

### 2.2 为什么不能是"一句"

直觉上"一句一个 chunk"最精确，实际会坏在三个地方：

| 问题 | 例子 | 后果 |
|---|---|---|
| **指代丢失** | "它必须在 load 之前执行" | 它是什么？向量里没有 |
| **信息不足** | "设置为 false" | 哪个字段？和上下文一起才有意义 |
| **区分度低** | "每个 job 都必须声明 size" 单独一句 | 和几百句同类句子都很近，排不出来 |

最后一条最致命：**短文本的向量区分度低**。
一句 20 字的话，在 5 万条的库里会有大量"看起来都差不多"的邻居。

**例外**：FAQ 型语料。一问一答本身就是自包含的语义单元，这时"一句"是对的。
所以规则不是"必须多大"，是"是否自包含"。

### 2.3 为什么不能是一整篇

| 问题 | 说明 |
|---|---|
| **语义稀释** | 2000 字讲 5 个主题，向量是 5 个主题的平均——和谁都像，和谁都不精确 |
| **硬截断** | `bge-small-zh-v1.5` 最大输入 **512 token**，超出部分直接丢掉，你也不知道丢了什么 |
| **引用粒度太粗** | 返回 2000 字让模型自己找，等于没检索 |
| **召回不可控** | 一段里只要有一句相关，整段就被召回，精确率被拉低 |

**512 token 是硬约束，不是建议。** 切完必须统计"超过模型上限的比例"，必须是 0。

### 2.4 正确粒度：一个"可独立回答的问题"

判断标准只有一条：

> **把这一块单独拿出来，一个不懂上下文的人能不能看懂？**

按语料类型：

| 语料 | 一个 chunk | 为什么 |
|---|---|---|
| 规则文档 | 一个 `##` 小节（标题 + 正文） | 每个小节讲一条规则，标题就是语义锚点 |
| pipeline YAML | 一个 job（太大再拆 extract/transform/load） | job 是"可复用"的原子单位 |
| FAQ | 一问一答 | 天然自包含 |
| 表格 | 一张表（不切行） | 切行会丢表头，行就没有意义 |
| 会议记录 | 一个议题的连续发言 | 按人切会把一个议题拆散 |

### 2.5 标题必须前置

**做法**：embed 之前，把标题拼到正文前面。

```python
# ❌ 只 embed 正文
"The most common defect is a mismatch between two things..."

# ✅ 标题 + 正文
"## Schema drift\n\nThe most common defect is a mismatch between two things..."
```

**为什么**：正文第一句经常是"最常见的问题是……"，没有标题根本不知道在说什么。
标题是这段文字最强的语义信号，丢掉它等于自残。

存储时同时保留结构化路径（`文件/小节`），用于引用和过滤。

### 2.6 粒度由查询决定，不是由文档决定

**先写 10 条真实 query，再看每条 query 需要多少上下文才能回答。**
那个范围就是 chunk 的大小。

```
query: "schema 漂移怎么发现"
  -> 需要：Schema drift 这一节（标题 + 3 段）
  -> 不需要：整篇 load-schema.md
  -> chunk = 这一节
```

反过来"先切好再想查什么"，切出来的粒度大概率不对——
因为你在按文档的结构切，而不是按问题的形状切。

### 2.7 两难时用 small-to-big

精确率和上下文是矛盾的：

- chunk 小 → 检索准，但返回的内容不够模型用
- chunk 大 → 内容够，但向量被稀释

**解法**：用小块检索，返回它的父块。

```
索引：每个 ## 小节再拆成 2~3 个段落块（小块，精确匹配）
返回：命中段落所属的整个 ## 小节（父块，完整上下文）
```

只多存一份映射，不改索引结构。这是解决"小 vs 大"的标准做法。

### 2.8 重叠：结构化文档不需要

| 语料 | 要不要重叠 | 原因 |
|---|---|---|
| 小说 / 转录稿 | 要，10~15% | 主题会跨边界 |
| 规则文档（按 `##` 切） | **不要** | 边界就是主题边界 |
| YAML（按 job 切） | **不要** | 切在 `- jobType:` 上，天然不跨 |
| 长表格 | 不要 | 表头重复即可 |

重叠的代价是**重复召回**：同一段内容在两个 chunk 里，top-5 里出现两次，浪费名额。

### 2.9 怎么用数据选粒度（而不是拍脑袋）

固定测试集，只改 chunk 大小，跑三档：

| 粒度 | R@1 | R@5 | 平均返回长度 | 超模型上限比例 |
|---|---|---|---|---|
| 128 token | ? | ? | ? | 0% |
| 256 token | ? | ? | ? | 0% |
| 512 token | ? | ? | ? | ? |

看两件事：

1. **R@5 什么时候饱和**——再大也不涨，说明粒度够了
2. **返回长度什么时候超过预算**——再大就塞不进 prompt

**但顺序是：先按语义边界切，再用数据微调。**
拿固定窗口（每 512 token 一刀）当默认，是没想清楚的表现。

### 2.10 本项目三种语料的具体选择

| 语料 | 切法 | 粒度 | 理由 |
|---|---|---|---|
| 规则文档（34 个 chunk） | 按 `##` 小节，标题前置 | 200~500 token | 一小节一条规则；实测 R@5 0.643 |
| pipeline（5,816 条） | **不 embed 原文**，embed 结构卡 | 1 张卡 | 原文 80% 是 schema 关键字，向量会按格式聚类 |
| 官方文档（数千页） | 按 `##`/`###`，超长再按段落 | ≤512 token | 模型硬上限 |

**第二条是关键判断**：

```
❌ 把 600 行 YAML 直接 embed
   -> 两条完全无关的 pipeline，文本相似度也很高
   -> 因为 jobType / connections / schema 这些词占了 80%

✅ 先投影成结构卡，再 embed
   job 链 + 连接器 + 目标层 + 变换类型 + 列名摘要
```

**embedding 之前先想清楚"什么算相似"。** 这不是模型能解决的问题，是特征工程。

### 2.11 向量侧的切分检查（和检索侧分开）

切完先跑这四个，不用模型：

| 检查 | 方法 | 通过线 |
|---|---|---|
| **超长比例** | token 数 > 模型上限的 chunk 占比 | **0%** |
| **邻居纯度** | 每个 chunk 的 top-1 邻居是否来自同一文档/同主题 | > 80% |
| **尺寸分布** | token 数的均值 / 标准差，看有没有极端值 | 无 10 倍离群 |
| **单主题** | 让模型总结这个 chunk，看是否需要"另外还有" | 主观抽检 20 条 |

**邻居纯度**是最有用的一条：如果 `Schema drift` 这一节的最近邻是
`Sizing and cost`，说明切分边界或者 embedding 有问题——它们不该相似。

### 2.12 一句话总结

> 切分的本质不是"把长文变短"，是**决定"什么算同一个意思"**。
> 一个 chunk 就是一个意思；embedding 只是把这个意思变成一个点。

## 三、测试集：怎么造，怎么防自欺

### 3.1 四层测试，各测各的

```
第一层  切分质量      无模型、无标注     结构 / 路径 / 覆盖 / 重叠
第二层  检索质量      要标注、不要模型   R@1/3/5、MRR、负样本
第三层  生成质量      要模型             pass_rate、轮数、token
第四层  端到端        要人               产物能不能被评审接受
```

**顺序不能反**：切分错了，第二层的数字没有意义。

### 3.2 三条造题原则

**原则一：不许从答案反推**

这是本项目真实踩过的坑：

```
拿 pipeline A 生成设计文档 -> 文档里全是 A 的表名和列名
-> 拿它当 query 去检索 -> 必然命中 A
-> 命中率 100%，但证明不了任何事
```

**正确做法**：query 必须来自"需求侧"——人写的需求、工单、或者改写过的描述。

**原则二：留一法**

候选集里不能有 gold。生成 A 时，A 必须从索引里排除。

**原则三：分层**

| 层 | 特征 | 测什么 |
|---|---|---|
| easy | 含表名/系统名 | 词面匹配的上限 |
| hard | 只有业务描述 | 理解意图 |
| negative | 语料里根本没有 | 该空的时候会不会硬塞 |

easy 和 hard 的**差值**就是"词面泄漏贡献了多少命中率"。
negative 测的是"不乱答"——大部分评测都不测这个，但它最接近真实体验。

### 3.3 测试集规模与成本

| 集合 | 条数 | 来源 | 耗时 |
|---|---|---|---|
| 文档 RAG | 50 | 每个 `##` 小节写 1~2 个问题 | 2 小时 |
| 结构检索 | 50 | 从卡片自动生成 query，人工确认 | 1 小时 |
| 语义检索 | 20 | 人工写（需要业务知识） | 1 小时 |
| negative | 10 | 故意问语料里没有的 | 20 分钟 |

**总计约 4 小时。** 这是整个检索项目里最贵的一步，也是最值钱的一步。

### 3.4 标注纪律

| 规则 | 原因 |
|---|---|
| 先读完所有候选，再写 query | 避免边看检索结果边改题 |
| 写完不再修改 | 改一次就是拿答案调参 |
| 隔天复核一遍 | 自己当天看不出自己的偏差 |
| 记录标注耗时 | 面试会问"这 50 条花了多久" |

**可选的加分项**：两个人各标 20 条，算一致率（Cohen's kappa）。
一致率低于 0.6 说明"什么算相关"没定义清楚，先对齐再标。

### 3.5 指标怎么读

| 指标 | 用途 | 陷阱 |
|---|---|---|
| R@5 | 有没有进候选 | 34 个 chunk 时 R@5 天然很高 |
| R@1 | 排得对不对 | 受标注歧义影响最大 |
| MRR | 平均名次 | 一条差样本能拉低很多 |
| **负样本准确率** | 该空的时候空 | 很少人报，但最影响体验 |

**必须同时报基线**：

- 随机（下界）
- 文件名关键词匹配（强基线）
- 无检索（对照组）

只报"我的检索 R@5 = 0.8"没有意义——文件名匹配可能也是 0.8。

### 3.6 一个已经踩过的坑

写 34 条样例的检索评测时，我为了"公平"，写 query 时刻意不抄原文关键词。

结果 BM25 的 R@5 只有 0.214，看起来"词法检索完全不行"。

**但这个结论是标注方式造成的**：query 全是被改写过的话，词法当然吃亏。

> **标注方式本身会决定谁赢。**
> 报指标时，必须同时报"query 是怎么写的"。

## 四、这件事和"要不要向量数据库"的关系

| 问题 | 切分/测试集能回答吗 |
|---|---|
| 要不要上向量库 | ❌ 不能。它只影响检索质量和规模 |
| 检索有没有用 | ✅ 能（第二层） |
| 检索有用，值不值得接进 Agent | ✅ 能（第三层） |
| 换了向量库会不会更好 | ✅ 能（同一套测试集跑两个后端） |

**顺序永远是**：

```
切分合格 -> 检索有效 -> 生成有收益 -> 才谈换基础设施
```

反过来做（先上库，再想怎么测），最后一定得到一个"跑得很快但没人用"的系统。
